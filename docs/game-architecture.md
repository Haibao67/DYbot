# 冬宴游戏 Bot 架构设计（v1）

## 1. 目标与边界

本设计以现有 `Core + Browser Worker` Bot 为接入基础，把冬宴币、牧场、赛马和彩票做成**服务器权威、可追溯、可定时结算**的文字游戏。果园及其全部联动暂不进入实现范围。

设计目标：

- 游戏规则不依赖聊天平台；同一条指令重放不会重复扣款或发奖。
- 所有群共用一个游戏世界：玩家余额、资产、排行榜、赛事、奖池和经济循环全局共享；群聊只是指令与通知入口。
- 所有货币变化都写入不可修改的账本；余额只是账本的快速投影。
- 定时任务可重复执行，且不会让训练、收获、开奖或赛事重复结算。
- 先支持文本指令与摘要；比赛“回放”先返回可复算的文字赛况，后续才接 2D 动画。

非目标：首版不做交易市场、玩家互赠、真实货币兑换、跨群资产转移和竞猜；这些会显著放大风控与经济平衡复杂度。

## 2. 总体结构

```text
聊天平台
  │  Browser Worker：登录、Socket 收消息、发送回复
  ▼
Core API：验签、去重、房间顺序、收件箱 / 发件箱
  ▼
Command Router：解析指令、权限和上下文
  ▼
Game Application Service：一个指令 = 一个数据库事务
  ├─ Account / Ledger      货币、库存、税、救济金
  ├─ Ranch                 动物、喂养、生产、出售
  ├─ Stable & Breeding     马匹、训练、亲密度、繁育
  ├─ Racing                报名、匹配、模拟、积分、奖励
  ├─ Lottery               购票、开奖、奖池、派奖
  └─ Notification          生成待发送文本，不直接调用平台
  ▼
PostgreSQL（生产）/ SQLite（本地）
  ▲
Scheduler：扫描到期事项并调用同一组 Application Service
```

现有 Worker 只负责运输，不能计算奖励、修改余额或决定比赛结果。这样可避免浏览器断线、重试或多 Worker 时造成游戏状态不一致。

## 3. 分层与代码落位

保留 `dzmm_bot/core.py` 的 HTTP 接口和 `dzmm_bot/worker.py` 的平台适配；把当前 `Store.receive()` 中的指令分派逐步搬出，建议目录如下：

```text
dzmm_bot/
  transport/       inbound/outbound、平台消息模型
  application/     command_router、各玩法用例、scheduler_jobs
  domain/          实体、规则、公式、比赛模拟（纯 Python）
  persistence/     SQLAlchemy 表、仓储、事务、迁移
  presentation/    中文消息模板、分页与格式化
  config/          数值平衡配置与赛事时间表
```

规则和公式位于 `domain/`，不得读取数据库或当前时间；应用层负责加载数据、开事务、调用规则、保存结果。这样可以针对繁育、赛马和价格波动写固定随机种子的单元测试。

## 4. 状态边界与核心数据

### 4.1 身份与全局世界

| 范围 | 主数据 | 说明 |
|---|---|---|
| 全局 | `players` | 平台玩家 ID、最新昵称、创建时间 |
| 全局 | `game_accounts` | `player_id` 唯一；余额、救济金日期、状态 |
| 全局 | `memberships` | 首次加入时间、权限、是否已领取新手马；不再按群重复加入 |
| 全局 | `world_state` | 唯一单例；彩票奖池、游戏日、版本、上次结算游标 |
| 群聊入口 | `room_settings` | 启用状态、通知偏好、管理员权限；不拥有游戏资产 |

私聊与群聊均访问同一份玩家资产；无需“切换群”。为了避免跨群刷屏，赛事结果默认只通知报名所在群，玩家也可在私聊查询自己的全局资料。

### 4.2 账本与库存

`currency_ledger` 是唯一的货币事实来源，字段至少包括：`id`、`player_id`（系统账户可为空）、`amount`、`reason`、`reference_type`、`reference_id`、`created_at`。`source_room_id` 可选地记录命令来自哪个群，仅用于审计与回复路由，不参与余额隔离。每个经济行为在同一事务中同时：

1. 校验 `game_accounts.balance` 足够；
2. 写入一笔或多笔账本记录；
3. 更新余额投影；
4. 写入业务对象及审计事件。

`reference_type + reference_id + player_id` 应具唯一约束，保证网络重试不会重复扣费或奖励。交易税作为独立账本记录进入 `world_state` 对应的系统奖池账户，而不是只存一个累加数字。

对于购买、报名和彩票，税额为应付金额之外的附加扣款；对于出售产品，税额从销售所得中扣除，即 `玩家实收 = 成交额 - ceil(成交额 × 0.05)`。两种情况都必须分别写入玩家账户与奖池账户账本，不能只在展示层计算。

可堆叠物品放 `inventory_stacks`（饲料、荣誉勋章、开发证碎片）；唯一物品放 `equipment_instances`（马蹄铁、皮肤）。所有数量变化也写 `inventory_ledger`。

### 4.3 玩法表

| 模块 | 主要表 | 关键状态 |
|---|---|---|
| 牧场 | `ranches`、`ranch_animals`、`ranch_products` | 当前等级、生产期结束、下次产出；产出按领取时补算 |
| 马厩 | `horses`、`horse_training_state`、`breeding_records` | 属性当前值/上限、亲密度、性别、繁育次数、训练次数、训练恢复锚点 |
| 赛事 | `race_events`、`race_entries`、`race_results`、`weekly_scores` | 报名截止、参赛快照、随机种子、结算状态 |
| 彩票 | `lottery_draws`、`lottery_tickets`、`lottery_payouts` | 售卖截止、3 个中奖号、开奖种子、结算状态 |

数值字段统一使用整数“最小单位”，避免浮点误差：币为整数；马属性以 `100` 为一整点（例如速度 25.50 记为 2550）；概率用万分比；时间以 UTC 存储、按 `Asia/Hong_Kong` 展示和排程。

## 5. 关键业务处理方式

### 5.1 延迟生产不依赖高频定时器

动物生产均保存“开始时间 / 到期时间 / 上次结算时间”。牧场升级在扣款且通过条件校验后立即生效，不创建升级任务。玩家查询、收获或后台扫描时，以服务器当前时间补算所有已到期批次，再把结果固化。

优点是 Bot 重启不会漏产，也不需要为每一只动物维持内存计时器。对产量较大的系统，单次补算设置合理上限（例如最多补 48 小时生产期内的批次），并保留明细或汇总记录供审计。

训练不创建异步任务。每匹马保存 `training_charges`（0–5）及 `charges_updated_at`；每经过 30 分钟恢复 1 次，最多存至 5 次。读取或训练前先按 `floor((now - charges_updated_at) / 30分钟)` 补充次数并推进时间锚点；训练扣 1 次、扣 20 币后立即增加属性与亲密度。该恢复间隔为配置项 `training_charge_recovery_minutes`，首版值为 30。

### 5.2 随机性可复算

购买马匹初始属性、训练增量、繁育系数、彩票号码和赛马过程都使用：

`HMAC(server_secret, 业务ID + 版本 + 预先保存的 nonce)`

派生出的伪随机序列。结果表保存 `rule_version`、`seed_commitment` 和必要快照；赛后可公布 nonce 或提供验证命令。不能直接使用进程级 `random`，否则无法排查争议或复现线上结果。

### 5.3 赛事结算

1. Scheduler 在固定场次前创建全局唯一的 `race_event`，写入赛道、长度、弯道、报名截止和规则版本。
2. 报名时锁定报名费、当日场次数、马匹可用性；截止时冻结 1–8 名选手及其属性、装备和赛前道具快照。
3. 未满 2 人的场次取消并原路退报名费；2–8 人照常开赛。首版不以机器人补位，避免伪造竞争。
4. `RaceSimulator` 基于冻结快照和种子分段计算位移、体力、弯道、冲刺，写入结果与精简事件流。
5. 同一事务内写名次、积分、奖励账本和待发送通知；`event_id` 是结算幂等键。

比赛结果一旦结算不可重算；调整公式只影响之后创建且使用新 `rule_version` 的比赛。

赛马规则首版采用以下固定口径：开赛时体力完全恢复；最后 200m 的冲刺自动触发，消耗当时剩余体力的 30%，并获得 `速度 × 1.3` 至终点。没有玩家手动选择。用户原文中的“冲刺必定处罚”按语义记录为“冲刺必定触发”；若确实需要加入惩罚效果，应在后续规则版本中另行定义。

适应力速度系数为 `max(0.70, 0.98^(15 - adapt))`（仅在 `adapt < 15` 时应用；否则为 1）。该系数乘入最大速度，赛道快照和比赛结果都保存实际系数。

### 5.4 彩票结算

每日 21:00（香港时区）关闭售卖并冻结当日票据，随后开奖。奖池计算需明确为：当期可分配余额 = 上期滚存 + 当日交易税 + 当日票价的 80%。中奖票按注数均分，除不尽的余数滚入次日奖池。每次开奖的状态机为 `open → closed → drawn → paid`，任一步可安全重试。

### 5.5 周赛

周日 20:00 选择前六天的全局积分前 16 名；并列使用“积分、最佳单场名次、最早达到该积分时间、玩家 ID”稳定排序。生成淘汰或单场决赛规则必须在 v1 开服前确定；建议首版为 **16 人单场冠军赛**，避免文案中的“参与”与实际赛制不一致。

## 6. 指令与交互约定

### 6.1 Bot 回复设计原则

所有面向玩家的回复由 `presentation/` 中的消息模板生成，不在领域服务或 SQL 代码中拼接。模板遵循以下原则：

- **准确简洁：** 先给操作结果，再给最必要的数字和下一步；不展示内部 ID、公式推导、数据库错误或无关说明。
- **格式清晰：** 标题独占一行；字段采用固定标签与换行；金额统一写作 `⨀ 120`；列表默认最多 5 项，超出时提示分页或筛选方式。
- **Emoji 作为视觉锚点：** 多使用但不堆叠。成功用 `✅`，失败/限制用 `⚠️`，余额用 `🪙`，牧场用 `🌾`，动物用 `🐔`/`🐑`/`🐄`，收获用 `📦`，出售用 `💰`，税收与奖池用 `🎟️`，赛事用 `🏇`。一条短回复通常使用 1–3 个相关 Emoji；数字、状态和指令仍必须可脱离 Emoji 理解。
- **行动明确：** 成功后只给一个最相关的后续指令；失败时说明原因和可行的改法，例如余额不足时同时给出缺少金额。
- **一致且可测试：** 所有金额、数量、时间和税额来自已提交的业务结果；模板快照测试覆盖成功、重复、余额不足、冷却/次数不足和系统错误。

示例：

```text
✅ 训练完成 🏇
速度 +0.84｜亲密度 +1
剩余训练次数：3/5
🪙 余额：⨀ 180

输入 /马厩 查看 查看属性
```

### 6.2 指令

**玩家指令只使用中文。** 斜杠后的主命令、子命令、帮助提示和下一步引导均使用中文；英文仅可用于开发内部的函数名、数据库字段和管理 API，不向普通玩家暴露。命令采用短中文主命令 + 空格分隔的中文子命令，所有资产变更先返回结果和全局余额变化：

```text
/加入                         加入全局游戏并发放新手资源
/我的                         余额、待完成事项、所属世界
/牧场 查看 | 购买 鸡 1 | 喂食 <动物编号> | 收获 | 出售 全部
/马厩 查看 | 训练 <马编号> 速度 | 喂食 <马编号> | 繁育 <父编号> <母编号>
/赛事 大厅 | 报名 <场次编号> <马编号> | 战绩
/彩票 购买 123 3 | 本期 | 历史
/排行 日榜 | 周榜 | 总榜
```

每个会改变状态的回复带一个简短的业务编号，例如“训练 `TR-…` 已完成，剩余训练次数 3/5”；查询可用该编号定位。长列表默认只显示前 10 项并提供页码。聊天事件的 `room + message_id` 同时作为命令幂等键。

## 7. 任务调度与可靠性

生产环境使用一个可持久化的 Scheduler（建议 APScheduler + 数据库作业表，或独立 worker），任务只负责寻找“应处理的记录”，实际结算仍走应用服务。关键作业：

| 时间（香港） | 作业 |
|---|---|
| 每分钟 | 可通知事项扫描；赛事报名截止处理 |
| 12:00 / 18:00 / 22:00 | 创建或启动日赛 |
| 21:00 | 彩票关闭、开奖、派奖 |
| 每日 00:00 | 日限制按日期自然失效，不批量改玩家数据 |
| 周日 20:00 | 生成并结算周冠军赛 |

Core 保持单实例时可先把 Scheduler 放进同一进程；迁移 PostgreSQL 与多实例前，必须给作业表增加租约或数据库 advisory lock，确保全局只有一个执行者。

## 8. 配置、版本与后台能力

所有价格、上限、概率、场次时间和公式参数写入版本化的 `balance_config`（JSON 或配置表），游戏事件保存使用的 `config_version`。管理员可发布新版本，但禁止直接改历史结果。

至少提供这些后台命令或内部 API：玩家账本查询、事件重放验证、指定业务单人工补偿、赛事/开奖结算状态、配置版本发布、冻结世界。所有管理行为写 `admin_audit_log`，不可通过 SQL 直接“加余额”。

## 9. 与原构想需先定稿的规则

以下规则已经定稿，并应固化为首版平衡配置：

1. **牧场升级价格**：第 L 级升至 L+1 的费用为 `round(200 × 1.5^(L-1))`，支付后立即完成。
2. **繁育**：父母不消失；每匹马终生最多繁育 3 次，每次成功繁育减少双方的剩余可次数。
3. **训练次数**：每位玩家可存 10 次；每 30 分钟恢复 1 次；训练即时完成并立即扣除次数与费用。
4. **适应力**：适应力低于 15 时，最大速度乘以 `max(0.70, 0.98^(15-adapt))`。
5. **体力与冲刺**：每场完全恢复；冲刺在最后 200m 必定自动触发。
6. **果园**：首版完全不实现，相关物品、联动、命令和数据表均不创建。
7. **全局世界入口**：新玩家只能成功加入一次；可在任意已启用群首次 `/加入`，之后任何群再次 `/加入` 都提示已加入。赛事结果只发送至报名群。
8. **交易税**：系统商店消费、报名、彩票购买和出售产品均按成交额征收 5% 流通税，使用 `ceil(成交价 × 0.05)` 向上取整并进入彩票奖池；购买类额外扣款，出售类从所得中扣除。

## 10. 推荐交付顺序

**M0：基础** — 迁移机制、全局账户、账本/库存、命令路由、管理员审计、测试夹具。

**M1：经济闭环** — `/加入`、救济金、牧场、物品、售价波动、含出售环节的交易税和基础排行榜。先验证玩家能“进入、生产、出售、升级”。

**M2：竞技** — 马厩、即时训练与次数恢复、繁育、日赛、确定性模拟、积分榜；不含竞猜和皮肤。

**M3：高风险扩展** — 彩票、周赛、赛马竞猜、装备联动、回放可视化。每个模块上线前用模拟玩家跑至少 4 周经济数据，观察币的产出/回收和新人追赶速度。果园留待后续独立立项。

## 11. 验收标准

- 同一平台消息、同一命令重试 100 次，余额和资产只变化一次。
- Core 或 Scheduler 在训练、开奖、比赛结算中途崩溃后重启，最终恰好结算一次。
- 同一玩家无论从哪个已启用群或私聊进入，看到并操作的都是同一份全局资产；不同玩家仍严格隔离。
- 任一余额变化能从账本定位到命令、赛事、收获或管理员补偿。
- 给定赛事快照、规则版本和随机材料，测试能得到完全相同的名次、奖励与事件流。
- 数值模拟能输出每日币产出、消费、奖池、各阶段资产分布；任何配置发布先通过该模拟。
