# 5.5B 执行文档：可配置、自适应发送节流

> 用途：以后用户明确要求“执行 5.5B”时，Codex 独立完成此阶段。本文不授权真实群试发或服务器部署；这些操作仍按当轮用户授权和 `AGENTS.md` 执行。

## 1. 前提、目标与范围

前提：5.5A 已交付可用的队列等待、平台 ACK、限流、`failed` 和 `uncertain` 指标。若指标缺失或口径不可信，先修复 5.5A，不凭“每分钟 30 条”的理论值盲目降速。

目标：将 `dzmm_bot/gateway.py` 当前 Socket 全局 2 秒间隔和同一私聊 5 秒间隔统一为可配置限速器；保守地根据**明确的平台限流 ACK**调整发送间隔。在未经真实验证前，默认行为与当前线上相同。玩家指令的原生 Reply、长消息拆分、入群成功私聊、公告发送路径均需保留。

本阶段只改 Socket 消息发送调度与相关配置/测试。Bot HTTP 主动公告通道保持现有发送行为；不要借本阶段重构 Core、队列领取或经济功能。

## 2. Codex 开始步骤

1. 先执行 `git status --short`、`git diff --stat`，阅读 `AGENTS.md`、`docs/ruihe-progress.md`、5.5A 的指标口径及维护手册入口。
2. 只读 `dzmm_bot/gateway.py` 的 `send_socket`/长消息分段、`dzmm_bot/worker.py` 的结果回报、`dzmm_bot/settings.py`、`.env.example` 和相应测试。确认实际平台限流文本及 `retry`/`uncertain` 处理，不能猜测新错误码。
3. 记录 5.5A 基线、已获授权的测试群范围及本轮是否包含部署。没有测试群授权时用 fake gateway 完成实现，线上参数保持默认值。

## 3. 配置与限速规则

建议配置项（采用项目现有环境变量命名风格，并在 `.env.example` 注明单位）：

| 参数 | 默认 | 用途 |
| --- | --- | --- |
| Socket 初始全局间隔 | 2 秒 | 与当前行为一致 |
| Socket 最小全局间隔 | 2 秒 | 未灰度前不自动提速；授权验证后才可配置为 1.5 或 1 秒 |
| Socket 最大退避间隔 | 60 秒 | 明确限流后的上限 |
| 同一私聊间隔 | 5 秒 | 当前行为保留，暂不纳入加速试验 |
| 成功窗口、降幅、限流冷却 | 有界配置 | 决定何时逐档降低/提高全局间隔 |

具体环境变量名称按实施时现有 `Settings` 确定。配置加载时验证 `0 < min <= initial <= max` 及窗口正整数；无效配置应使 Worker 明确启动失败，不能默默采用危险值。正式服务器已有 `.env` 缺少新项时使用上述安全默认值。

- 所有 Socket 发送，包括失败后**确需**拆出的每一段，先通过同一全局限速器预留时隙；同一私聊还要满足私聊间隔。时间使用注入的单调时钟，测试使用 fake clock/sleeper，不等待真实秒数。
- 只有已识别的平台限流（例如当前代码处理的“请稍后再试”）触发退避；普通重复内容、长度拒绝、网络超时、未知 ACK 不作为“提高速率成功”证据。限流后维持现有 outbox `retry` 语义和 60 秒可用时间，不能在同一调用里立即再发。
- 连续成功且冷却期内没有限流时，按配置小步降低间隔，最低不低于配置下限；限流时立即回退，随后的成功重新累计。Worker 重启时先回到安全初始值，除非有已验证的持久化方案。
- 生成 Socket 消息 ID、原生 `reference`、北京时刻尾标、长回复分段和 `uncertain` 处理保持原契约。不要用 Bot HTTP 替代玩家原生 Reply。

## 4. 实施顺序

1. 把全局和私聊等待逻辑提取为一个小型 limiter，替换 `Gateway.send_socket` 中主消息与分段消息的重复计算；避免第二套发送队列。
2. 将 `Settings`、`.env.example` 和运维说明加入安全默认配置。向 5.5A 指标增加当前有效间隔、最近明确限流时间和调整次数，供管理员只读查看；不得输出 Token 或消息正文。
3. 保持 Worker 一次领取一条出站任务。单任务失败仍按现有 result API 回报；不要为提速绕开 outbox 状态机。
4. 用模拟 ACK 完成定点测试，再运行 Socket/Worker/Reply 相关回归。达到发布门槛后，如果**本轮另有部署授权**，按维护手册发布；默认参数上线后先确认结果与旧版相同。
5. 真实降速间隔试验只在已授权测试群进行：先设最小 1.5 秒观察一段有足够样本的窗口，再考虑 1 秒。每档记录成功 ACK、限流、`failed`/`uncertain`、P50/P95 排队等待和发送耗时；任一错误持续增加立即恢复 2 秒并记录原因。不要向正式群批量发送合成消息。

## 5. 必须覆盖的测试

- fake clock 下连续普通回复满足全局间隔；同一私聊同时满足 5 秒；跨群不能绕过全局间隔。
- 长消息首次被明确拒绝后各分段仍限速、引用原消息、尾标正确；部分分段成功后的不确定结果不被自动重发。
- 明确限流 ACK 提高间隔并冷却；非限流拒绝不提高；成功窗口逐档恢复但不越过配置下限。
- 超时、Socket 断线、Worker 重启、配置缺项/非法值、回复 ACK 丢失：不造成负间隔、忙循环或二次发送。
- 与 5.5A 的指标对照 10/100/500 条假请求，记录同负载的排队时间。所有测试固定时间，不使用 `sleep`。

本阶段原则上不需要 schema 迁移；若实际实现必须新增数据库字段，追加 Alembic migration 并按维护手册做旧库副本演练。阶段末执行一次全套及隔离 Core/Worker 冒烟；测试没跑或平台试验未获授权时标记 `NOT RUN`。

## 6. 验收和回退

验收必须同时满足：默认配置与旧版发送时序相容；在已获授权的试验档位，P95 排队等待比 5.5A 相同负载基线降低，且明确限流、`failed`、`uncertain` 无持续增加；所有玩家回复仍引用其原消息。不要把“1 秒理论每分钟 60 条”当实测吞吐。

若平台拒绝增加，先将最小/初始间隔恢复 2 秒；配置回退后仍有异常，按维护手册恢复已备份代码并核对 Core、Worker、心跳及队列。报告实际配置、样本数、P50/P95、失败数、回退动作和未验证项。只有 5.5B 稳定后才进入 5.5C。
