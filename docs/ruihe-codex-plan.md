# DYbot → 瑞禾：Codex 项目更新实施计划

> 基准：用户上传的 `DYbot-main.zip`（GitHub 导出提交 `77ea54058809bfb020c0f566e446227bbce6d283`）；产品依据：`ruihe.md`；新增强制需求：Bot 使用聊天平台的**原生引用/回复消息**功能，回复发送该条指令的玩家原消息。以本地代码和本文件为准，不假设服务器代码、平台 API 或生产数据库与 ZIP 完全一致。
>
> 目标是逐阶段交付可运行代码、迁移、测试和文档，而非仅生成伪代码、静态面板或一份新架构建议。不得在一轮中擅自将所有未来玩法判定为已上线。

## 0. Codex 可直接执行的总指令

你是此项目的实施工程师。先读取 `AGENTS.md`（如有）、`docs/game-architecture.md`、`docs/m1_v0_0_1.md`、`docs/server-guide.md`、`dzmm_bot` 源代码及测试，并把用户提供的 `ruihe.md` 保存为项目可追踪的需求文件 `docs/reference/ruihe.md`（如果已有则不覆盖）。按本计划从 P0 开始分 PR/分提交开发，保持原 Core + Browser Worker、已存在的消息队列、玩家全局账户和数据库数据。每个阶段必须做到：代码实现 → SQLite 测试 → PostgreSQL 迁移/集成验证（可用环境下）→ 文案快照 → 实际群内验收说明 → 更新文档。禁止把示例玩家昵称、等级、动物、价格、进度和剩余分钟写死进业务代码。任何无法从参考文档和实测协议确认的参数，进入 `docs/ruihe-open-questions.md` 并使用功能开关隔离，不可暗自臆造。

每阶段输出：变更文件清单、数据库迁移说明、执行的测试及实际结果、与参考输出的差异、未实现项和下一阶段依赖。不要求在未接入真实账号时伪称原生引用已经经过真实群验证。任务超过一次会话时，先完成 P0，不要留下半迁移的数据库状态。

| 宠物/挖宝/玩家店铺/金融 | 尚无瑞禾对应业务表和服务 | 分模块独立扩展，依赖经济、物品、调度、交易原子化 |

重要：`docs/game-architecture.md` 中 M2 赛马/M3 彩票的旧排期属于另一套路线；本计划按用户最新给出的瑞禾参考推进。不能把“奖池已有余额”误说成“彩票购票和开奖已实现”。

## 2. 红线与实施约束

1. 保留 FastAPI Core、Browser Worker、现有 `Store` 事务性 inbox/outbox、授权、白名单、房间顺序和发送状态机；不改回 `legacy_webhook.py`。
2. 不删除旧指令。新增 `/牧场`、`/买动物`、`/喂食`、`/收取`、`/行情`、`/出售`、`/加工` 等别名时，旧 `/牧场 查看`、`/牧场 购买`、`/牧场 收获` 等仍有效，最终调用同一业务用例。
3. 保留原有 DB 的 `players`/`game_accounts`/`ranches`/`ranch_animals` 等主键。只做新的 Alembic 版本 `0003_...` 起的**前向迁移**；先备份并在数据库副本演练。不能编辑已经发布的 `0001_foundation`、`0002_ranch` 或 `m1-v1.json`。
4. 已发行的 `currency_ledger`、`inventory_ledger`、`game_events`、`game_config_versions`、`admin_audit_log` 有不可变触发器，不修改/清空历史。不通过直接 `accounts.balance += ...` 绕开账本。
5. 业务事务内原子完成：检查状态和余额 → 写业务对象 → 货币/库存账本及投影 → 审计事件 → Outbox；如果失败全部回滚业务，仅保留去重与失败反馈（沿用现有 savepoint 语义）。
6. Python 货币单位：定义整数最小单位，例如 `1 币 = 100 分`。**当前生产旧余额/账本是整数币**，不得在未经迁移策略验证时直接将旧金额乘 100、改列意义；先做 `Money` 适配/正式迁移和历史对账，在旧/新格式共存期间明确版本，禁止显示 `4.34` 却扣 `4`。
7. 所有时间由服务端给定 `now`，内部 UTC 时间戳，展示及每日 0:00、09:00、20:00、20:30、21:00、周日 20:00 使用版本化 `Asia/Hong_Kong`（UTC+8）；不得用客户端时间或每个 worker 的内存定时器作为结算事实。
8. 不因消息发送失败重复扣款；发送状态 `uncertain` 需保留人工确认，不因引用失败重新执行游戏业务。
9. 有交易、奖励和随机结果的功能必须具备幂等键、审计和服务器可复核规则；长消息在真实平台的长度限制下分页/分段，且每段均回复同一原命令。

## 4. P0：原生回复、协议与基础设施（最高优先级）

### 4.1 先确认平台协议，不要编造字段名

- 阅读仓库 `dzmm_bot/gateway.py`、`browser_socket.py`、`core.py`、`store.py`、`persistence/transport.py`、`test_core.py`；查阅有权限取得的平台官方说明，或在**已授权测试群**用浏览器 DevTools 观察“用户手动引用某条消息发送文本”的真实出站 Socket/API 载荷与回包。只记录必要结构，过滤 Token/Cookie/私人聊天内容。
- 分别确认 Bot API `/api/bot/send-message` 与 Socket `message:send` 是否支持原生引用；哪个字段承载被回复消息的 ID、是否还需引用作者 ID/内容/嵌套对象、消息失效的错误码、服务端是否会忽略未知字段。没有实际证据前，不要使用自猜的 `reply_to` 字段作为完成标准。
- 若 Bot API 不支持引用但 Socket 支持，**引用任务优先走可验证支持的 Socket 通道**；非引用任务维持旧路由；仅明确拒绝/失效时按已确认策略降级，不把网络超时当作发送失败去切换重发。

### 4.2 元数据贯穿全链路

建议在 outbox 加 `reply_to_message_id`（同房间消息 ID）、`reply_to_sender_id`（原命令发送者）、可选 `source_inbound_id` 或语义等价字段。`Inbound` 现已有 `room/message_id/sender/name/text`，不要增加第二个含义相同的 ID。`Store.receive()` 在同一数据库事务写 outbox 时固化引用；`claim()` 返回并保留字段；`Worker.drain_once()` 不自己猜目标；Bot API/Socket 适配器由一个 `OutboundMessage`/adapter 转为**实测平台支持的结构**。

要求：

- `/帮助`、`/加入`、`/我的`、`/救济`、牧场/加工厂/其他业务指令及所有可控失败、格式错误均原生引用**该次消息**。
- A/B 两玩家同群相邻下指令，各自回复原 ID；不同群相同 message ID 仍按房间隔离；原消息作者为依据，不引用上一位玩家。
- 接收机器人自己的消息、未知/禁用群的消息仍忽略，不能形成回复环。
- 若服务端推送的用户昵称字段有可信来源，从中抽取昵称；不能把 `"玩家"` 写回已有真实昵称。内部必须始终按玩家 ID 授权，昵称只用于展示。
- 原消息不存在或引用协议**确定**不支持时，记录经过脱敏的原因与退化指标，明确的一次性普通文本降级（可在群中以 `@` 补充提醒，前提是平台支持且不影响内容）；发送状态不确定则维持 uncertain，禁止二次投送。
- 主动的 09:00 行情播报/全群灾厄等**没有触发命令**的系统通知不应引用无关玩家。玩家发起、延迟 30 秒的挖宝结果应仍引用**发起挖宝的原命令**。

### 4.3 P0 测试/验收

- 扩展 `test_core.py`：入站 ID 持久化、claim 回包、Socket 实际构造、Bot API 支持与不支持分支、显式失败降级、超时不双发、租约过期 uncertain、重启持久化、原消息失效、两玩家并发与跨群。
- 加 JSON 协议样例 fixture（敏感字段脱敏），同时保留旧无引用的 mock 测试。
- 真实群手动发 `/加入`、`/我的`、错误指令、长面板，两名测试玩家交错操作；证据是平台 UI 的“回复该条消息”效果，不是正文里出现玩家名字。
- **交付判定：** P0 测试通过且实际群原生 Reply 验收通过，或若平台确不支持，提供证据、功能状态及降级说明，不能谎报达标。

## 5. P1：中文指令与瑞禾排版协议

### 5.1 路由/别名

使用统一指令注册或薄 `aliases` 层，将以下新形式路由到对应业务，且不破坏 `/牧场 查看` 等旧格式：

```
/瑞禾玩法  /菜单 [分类]  /牧场  /买动物 鸡 [数量]  /买精饲料 [数量]
/喂食  /喂食 精  /收取  /行情  /出售 鸡蛋 [数量]
/买入 鸡蛋 [数量]  /回收 [鸡|羊|牛|闪光鸡...] [数量]  /牧场升级
/加工  /加工厂  /投产 蛋糕  /取货  /加工厂升级
/加急 [线号]  /取消投产 [线号]  /资料
```

**易冲突处：** 旧 `/牧场 喂食 <动物编号>` 只喂单只；新 `/喂食` 意在全牧场统一续喂。二者是不同 use case，不能让空参数误调用旧函数；不支持的玩法必须明确“尚未开放”，不可显示不存在的菜单可用。

### 5.2 展示层拆分

保留入口 `presentation/messages.py` 的兼容性，新增 `presentation/ruihe.py`、`presentation/formatters.py` 或同职责模块；业务层返回结构化数据，不返回排版好的长字符串。统一：

- `—— 🏡 昵称 【称号】 的牧场 ——`、`—— 🏭 昵称 的加工厂 Lv.N（…）——` 标题；没有称号时自然省略，不显示 `None`。
- `｜` 同行字段、全角缩进 `　` 子行、`▓░` 文本进度条、`⏰` 剩余饲料、`📈📉` 价格趋势、`💡` 提示、尾行 `指令：...`。显示信息与实际玩法状态一致。
- 时间进度统一 `0 ≤ completed/total ≤ 1`，负时间显示“已完成/待收取”，不能出负小时、`NaN`、大于 100% 的条。
- `money`/`quantity`/`duration`/`remaining`/`bar`/`name_escape` 由公共 formatter 生成；价格最多 2 位小数、余额和税显示一致；不输出内部英文代码或未暴露 ID。
- 牧场按鸡/羊/牛聚合显示、按生产状态/精料/亲密分类；不同状态的同种动物不能被错误合并成一条误导玩家。
- 0 只动物、空库存、满级、满线、停产、未加入、冻结、跨时区、超长名字、表情宽度、群平台折行都要有模板样例。
- 两段真实范例分别做 golden snapshot：牧场面板与加工厂面板；第三个范例做投产成功回执。示例数字只存在 `tests/fixtures/`，应用渲染需来自服务返回。

建议语义结构：`CommandResult(payload, outbound_context)`；最终由 Store 将 `render(result)` 与引用元数据共同持久化。兼容原 `render(result, reference, stage)` 的已有测试和管理用途。

## 6. P2：牧场玩法改造与线上数据兼容

### 6.1 以瑞禾文档为目标，旧参数不得默默延用

| 参数 | 原 M1 | 瑞禾说明 |
|---|---|---|
| 动物基础价 | 鸡 50 / 羊 120 / 牛 300 | 相同；“鸡 53 币起步”可由 50 + 5% 向上取整税得到 |
| 产出间隔 | 鸡 2–4h / 羊 10–14h / 牛 6–10h | 鸡 3–5h / 羊 9–12h / 牛 6–10h |
| 生产/饲料窗口 | 48h，过期不可再喂 | 新购自带 12h 饲料、每次喂养续 12h，宠物狗 14h，断喂停止产出但已产商品不腐坏；超 10h 亲密归零 |
| 基准价 | 蛋 5 / 毛 20 / 奶 15 | 奶 18 明确；蛋/毛未重申，建议沿用 5/20 并在新配置显式写明 |
| 牧场等级/容量 | 最高 9，容量 `3 + 2 × 等级` | Lv9 容量 21/21；每次 +2，与当前公式相容 |
| 晴/雨/旱/闷/风/丰收祭 | 无 | 全局每日天气及产量加成；丰收祭概率 10% |
| 市场 | 整数、±15%、随时计算 | P3 实现 30min 快照、基准价 50%–160%、小数 |

制作新的配置快照（例如 `ruihe-ranch-v1`），`world.config_version` 只在迁移与数据兼容方案确认后切换。旧 `ranch_animals.rule_version` 的旧生产周期必须先结算到切换时刻或保留旧周期规则，不得 retroactively 重算历史。注意 `seed_for` 当前使用 Core token 作为 secret；如更换 secret，需验证旧种子记录可复核且不可破坏历史。

### 6.2 推荐数据演进

在现有单动物 `ranch_animals` 上逐只增加（或以 1:1 `ranch_animal_care` 表承载）`fed_until`、`last_feed_at`、`unfed_since`、`affection` (0–9)、`on_time_streak`、`premium_until`/`premium_cycle`、`is_shiny`、`care_rule_version` 等；时间状态必须可计算，不能仅靠展示虚构；为天气提供全局 `daily_weather(day, kind, seed, config_version)` 唯一行。所有变更有业务事件和唯一引用。

初始化历史动物时制定清楚策略：现有 48h 生产周期如何映射 12h，不允许让老玩家已付费剩余生产期直接归零；可为历史动物保留原 `rule_version` 至旧有效期结束，首次按瑞禾规则喂食再进入新周期；也可统一给予补偿性的 `fed_until`，须由迁移说明和测试固定一种策略。历史未定义亲密/闪光不可自作主张随机补发。

### 6.3 生产与喂食用例

- `/喂食` 面向玩家所有动物，批量校验/扣料/续窗，按每只逐步更新、全量原子提交；`/喂食 精` 消耗提前购买的精料，产量 +15%、亲密额外 +1；和天气、连喂、组织 Buff 的乘法合并由纯函数计算，并定义舍入/小于 1 的产出规则。
- 准时补喂亲密+1（每点 +2%，最多 9）；连续准时 3 次起额外 +10%；断喂超过 10h 亲密清零；过期后的恢复策略以瑞禾规则为准，不继承 M1 的“永远不可喂”限制。
- 断喂不腐坏、不会补产断喂期间的商品；收取操作必须先结算截止点内产出，随后库存入账，重复 `/收取` 无法双收。
- 同种不同精料、闪光、亲密、待收、间隔时不得为了面板聚合丢失实际状态；闪光出现率/增益**参考文件未给**，先实现字段与展示能力，抽取/收益规则待定稿。
- `/回收 [闪光]动物 数量` 返回清单与 6 折回收；价格、税费是否叠加按配置明确，不能直接硬编码；先收取待收商品再回收或记录销毁规则，避免资产丢失。回收扣 `used_capacity` 并使相关动物不可继续生产。
- 全服天气按日期唯一确定；雨季羊毛 ×1.5、旱季蛋 ×0.7、闷热奶 ×0.8、晴天全产 ×1.2、微风无加成、丰收祭全产 ×1.5；宠物/道具免疫坏天气后处理。

## 7. P3：市场、金额精度及倒买倒卖

- `/行情` 返回全局一致的 30 分钟 market tick，品类价格和 📈/📉/持平、涨跌标签可由持久化 tick 对比派生；行情发布不要求每秒重算；服务重启后同一 tick 返回相同结果。幅度基准价 50%–160%，具体随机/趋势算法参考文件未定义，需要在 `docs/ruihe-open-questions.md` 记录并实现可复算、版本化、受限的规则，不得冒充原版算法。
- 购买 `/买入 鸡蛋 10` 价格 = 当前 tick 的买入基价再加 5%；出售 `/出售 鸡蛋 10` 当前卖出基价减 5%；需明确对每单/每件的舍入，参考“买卖有10%价差”是名义价差，复算需精确；原 5% 交易税进入奖池的口径**与瑞禾的买卖手续费是否为同一费用需定稿**，不能无意叠收。
- `/买入` 每玩家每 30 分钟累计限购 200 币（服务端时间，原子检查），跨群共享，不以发消息次数计算。
- 二位小数估值：`quantity × current_unit_price`，显示 `鸡蛋x280｜现价 4.34 📈｜约值 1215.2` 等；库存基价来源统一，静态加工品示例可保留固定价。
- 原 M1 的 `currency_ledger` 和 `accounts.balance` 使用整数币，P3 必须提交细分币的数据库迁移或可审计的金额层转换，测试：旧 100 币账本余额仍为 100 币、新小数买卖守恒、退回/补偿/救济/排行/奖池均正确。建议先在测试库双轨验证，再在维护窗口切换；不能仅把模型 `BigInteger` 改 `Float`。
- `market_transactions` 需可表示买入、税/手续费来源、tick ID、单位价格最小单位，必要时新表/字段前向迁移并保留旧记录旧单位的语义。

## 8. P4：加工厂核心（必须复刻两个实际输出样例）

### 8.1 规则

| 层级 | 配方 | 基础工时 |
|---|---|---|
| T1 | 蛋 ×3 → 蛋糕(固定 18)；羊毛 ×2 → 毛衣(50)；牛奶 ×2 → 奶酪(40) | 1h |
| T2，厂 Lv2 起 | 蛋糕 ×2 + 奶酪 ×1 → 礼盒；毛衣 ×2 + 羊毛 ×1 → 羽绒服；奶酪 ×2 + 鸡蛋 ×1 → 奶酪拼盘 | 2h |
| T3，厂 Lv4 起 | 礼盒 + 羽绒服 + 奶酪拼盘 → 大礼包(基准 500) | 4h |

参考面板还列出“丝巾、冬宴鱼宴、雪绒毯”，但配方/价格/解锁条件未给，先显示为“待开放”或待配置，不允许玩家投产无配方物品。T2 部分加工品价格随行情变动，价表待定。

### 8.2 数据与状态机

- 建议 `factories(player_id, level, efficiency, line_count, rush_used_on, rush_count, version)`、`factory_lines(id, owner, line_no, state, product_code, started_at, finishes_at, recipe_version, captured_inputs_json, bonus_snapshot_json, seed_commitment, result, collected_at, ...)`；独立配方版本/静态快照写入配置。
- 状态示意：`idle → running → ready → collected/idle`，取消为 `running → canceled/idle`；失败结果作为可审计的 `ready_failed` 或等价状态；重复 `/取货` 不得重复入库。
- `/投产 蛋糕` 选择最小可用线号、原子扣材料并冻结配方、工时、效率、加成与随机种子；返回实际昵称/组织名/线号/计算后剩余分钟与固定/浮动售价说明。
- `/加工厂` 展示等级、线数、效率、每条进度和剩余时间、已开放配方、下一次升级的材料和新线数/效率、今日加急次数、当前失败率、指令。
- T1/T2/T3 收工时间以 `started_at + effective_duration` 计算，展示示例“3号线约22分钟”须由实际等级及 Buff 推出，不能为迎合样例写死 22。
- `/取货` 一键收取所有可完成线；未完成线不动；失败/暴击（双倍）由确定性种子决定、记录快照；停机恢复与高并发操作仍准确。
- `/加工厂升级` 按配置实现扩线和提速；参考说明说“满级5条线，36分钟/单”，样例却为 Lv5 已5条线、下一次升级可达6条线 ×0.48，**互相冲突**：默认 P4 只实现已有明确的 Lv1–5 基础模式，Lv6/自动化核心扩线作为可配置扩展并列入待定事项，不直接把两者硬拼。

## 9. P5：加工高级操作与商铺增益

- `/加急 [线号]` 当前日上限 3 次，价格依次 10/20/40 币（是否再计 5% 税需定稿）；原子扣费→完成指定进行中订单→留审计；重试不重复计数。
- `/取消投产 [线号]` 按生产进度返 80%/50%/20% **材料**，阶段阈值文档未给，需配置/定稿；必须记录投入快照、已返数量、原订单终止，禁止取消+取货双得。
- T3 失败率、暴击率、加急/大师餐影响必须由配置 + seed 解释；参考“当前失败率 4%（T3减半）”是一个样例值，不等于全品类永久 4%。
- 增益道具及配方：铁匠铺（毛刷/铜铃/暖棚）、餐馆（开工宴/大师餐）、裁缝铺（礼服/工装围裙）；制作库存、店铺进货、购买即用、起止时间和倍率快照分别记录。`/资料` 查询所有生效 Buff 及过期时间；“连吃续时叠加”区分**续时**与**倍率叠乘**，禁止无上限永久叠加。
- 玩家店铺经营/求购单另在 P7 统一上架系统中完成，不为每种店铺写一套交易账本。

## 10. P6：宠物系统

- `/买宠物蛋` 50 币、全服每自然日最多 10 枚、48h 后 `/孵化` 手动触发、初始体 3 天成长完全体；每日忠诚 -8；`/喂宠物` +10（每日≤3）、`/撸宠` +3、`/逗宠` +5；忠诚 <60 效果失活；“饿两天出走”要定义最后有效喂养时间与出走状态。
- 宠物粮 `蛋×1+奶×1→3份`；毛线球 `羊毛×2→2件`，材料与产物走库存账本；杂货铺经营联动独立开启。
- 文档说 18 种宠物，但明确列出 12 种：猫、狗、仓鼠、鹦鹉、兔子、刺猬、猫头鹰、狐狸、松鼠、浣熊、天鹅、雪貂。**另外 6 种的身份及能力未知，禁止凭空补全。**已列出者也需逐个验证外部依赖玩法是否上线（例如偷菜/明日情报/免费广播），未上线的被动不可假装生效。
- 异色✨ 8%、效果×1.2、繁育 25% 遗传；变异🧬 2%、不遗传；同种完全体繁育冷却 7 天；蛋与繁育都记录源事件/种子，避免重试刷稀有。
- `/斗宠` 需要解析**玩家引用的他人消息**来定位对手（这与 Bot 出站引用是不同方向的协议功能）；确定对手同意、押注锁定、消除撤回/跨群冒名之后才上线。周日 20:00 冬宴杯及冠军池分成需唯一赛次 + 幂等发奖。

## 11. P7：挖宝、求购及装扮

- 挖宝用持久化作业 `pending → revealed → choice_pending → resolved`：消耗碎片 → 30s 后出结果，若密室则 60s 内 `/深入`（60% 再得一笔/40% 追回一半）或 `/撤退`；超时默认策略需定稿。挖宝揭晓属于原指令的延迟回复；选择指令结果回复选择消息。重启后不会丢定时结果。
- 11 事件“空坑/宝箱怪/宠物蛋/物资箱/全群红包/宝匣/遗迹”等概率及奖励明细文档不全；做版本化配置表，未定权重的奖励池不得对外上线。连黑 3 次保底、天气空坑+5%、兔子物资箱+5%、幸运铲稀有率翻倍 3 次作为独立可测 modifier。
- 黄金藏宝图免碎片且必出宝匣级以上；罗盘 30 币、1h 掉率×3；藏宝图可转售时需原子保证只有一个持有人。
- `/求购 名称 数量 单价` 保证金冻结（**冻结不是销毁/扣税**），24h 过期解冻；`/收购行` 看全服，`/卖给 店名 编号` 成交佣金 8% 入池。竞争售卖、部分成交、撤单、余额/库存不足不能超卖；可上架稀有物品。
- `/装饰店`、`/边框`、`/称号`、`/签名`：装饰 +1%～3% 的叠加上限及随机价待定；每周限定轮换固定世界日期与种子，个人面板真实显示玩家启用的装扮。

## 12. P8：跨系统内容（按已确认规则单独立项）

- `/签到`、`/打工`、`/任务`、交易挂单/外贸托运/商队砍价、灾厄全服抗灾、银行吃息/基金/拍卖、AI 问答/副本、21:00 彩票、宠物斗技：瑞禾文档多处只有玩法名和时间，没有完整数值、权限、结算和风控。先建菜单分组和“未开放”状态，再逐个补独立玩法规格，不把概要当详细可执行规则。
- 与旧 `docs/game-architecture.md` 的赛马、彩票设计有交集但非同一套玩法；复用底层账本/世界调度/随机验证能力，业务规则须明确选定版本和上线次序。

## 14. 需求冲突/缺项清单（不得静默解决）

1. 加工厂 Lv5“满级5条线”与面板“Lv5 升 6 条线、效率×0.48”：需要决定 Lv6 是否真实开放、升级成本。

3. 旧动物生产 48h 且不可复活，瑞禾 12h 可重喂；需要线上存量保护/补偿方案。
4. 小数价格与旧整数币账本：采用分作为账户底层单位还是引入独立价款清算层，必须确定并演练。
5. “18 种宠物”只列 12 种；其余 6 种、稀有分层、基础战斗属性不详。
6. 闪光农场动物的出现率/增益/回收优先级（除了指定回收闪光）不详。
7. 价格 30min 刷新区间有上下限，但更新分布/涨跌标签、T2 加工品价格规则未给。
8. “连吃续时叠加”的倍率和时长上限、精料消耗单位、整数产出小数倍率的取整不详。
9. 加工失败/暴击概率、返料进度阈值、Lv2/Lv4 解锁及升级费用/材料、自动化核心来源不全。
10. 挖宝消耗碎片数、11 事件具体概率、过期密室默认行为、宝匣奖励表不全。
11. 彩票票价、奖项结构与当前奖池口径需要在新旧设计之间选版本；银行/基金/拍卖细则不全。
12. 原生引用平台协议未在 ZIP 内定义，不得认为随便加字段就能成功。

策略：P0/P1/P2 已明确部分先做；对于所有未定规则，在代码中以未开放或配置缺失拒绝，不提供虚假的可操作菜单；Codex 应在阶段报告集中列出**确实会阻塞下一阶段**的最少问题。

## 15. 全量质量/经济/运营验收

**功能与输出**

- `/牧场` 的标题、等级容量、天气、动物分类、亲密/连喂/精料、六格进度、待收数、剩余时间、库存现价趋势、估值、尾部指令均来自测试时间固定的真实状态。
- `/投产 蛋糕` 能返回正确线号/发起者昵称/组织名（无组织时隐藏）/实际剩余时间及“固定售价18币”，不泄露其他玩家订单。
- `/加工厂` 能逐线展示 8 格进度、配方可用级别、下一等级、加急次数、失败率/指令；版本冲突部分按已批准口径。
- 每一条**玩家主动指令**的成功与错误反馈在真实群原生回复该消息；主动公告不乱引用。长文本分页每段都引用正确原消息。

**数据与规则**

- 同消息重发、两玩家并发、跨群相同消息 ID、重启后收取/取货、重复加急/取消/出售/领奖、取消与收取竞态均不重复记账/发奖。
- 账本余额/库存投影与流水逐玩家对齐；奖池收支/折旧/销毁各有来源；不能有负余额/负库存/重复出货。
- 固定 seed 的天气/行情/动物产出/加工暴击等可复算；服务器时钟边界（00:00、30min、12h、14h、10h 断喂、每周日）有单测。
- 冻结玩家不可交易/领取但仍可查询；跨玩家动物/流水线/宠物/订单 ID 严格校验归属；开关关闭后保留历史查询和数据。
- 消息长度、API 429、断网、ack 不确定、浏览器重登、重复连入、房间禁用和长期离线都经过模拟。

**测试与上线指令**

```bash
python -m pip install -r requirements.txt
python -m unittest discover -v
python smoke_test.py  # 先查看脚本所需环境，勿在未配置时指向生产
python simulate.py    # 同上，固定随机种子与时钟，生成 28 天经济报表
```

在可用 PostgreSQL 测试实例额外跑 Alembic `upgrade head`、旧库备份恢复迁移、并发交易及账本核验；如果本环境缺少 `python-socketio`、Playwright/Chrome 或数据库，标明“未跑/原因”，不能写“全测试通过”。灰度顺序：本地独立 DB → 全新 PG 测试库 → 带匿名生产快照测试库 → 白名单测试群 → 少量已启用群 → 全群。上线前快照备份、输出迁移预检查与回滚方案；数据迁移不可逆时回滚应用靠兼容代码，真正还原须恢复验证过的备份。`README.md`、`docs/server-guide.md`、配置快照、功能开关文档和变更日志同步更新。

## 16. Codex 第一轮实施的明确任务（请从这里开始）

**本轮只做 P0 + P1 的最小可运行版本，不抢跑改历史经济或将全部瑞禾玩法宣称上线：**
