## 1. 总原则：少读、少改、少跑、不错报

**目标不是省掉必要测试，而是按风险集中测试，避免把整仓阅读、全量测试和长报告放进每一次小改动。**

1. 一次处理**一个阶段中的一个可验收垂直切片**（例：`入站 ID → outbox → claim → Worker → Reply adapter → 测试`），不要“一口气实现 P0–P9”。
2. 先看变更范围，再读相关文件；不重复打印已理解的大文档、完整源码、完整测试日志。
3. 先为 bug 写/选**最小复现测试**，再改代码；尽量一次完成相互依赖的修改后集中跑一轮相关测试，而不是每改一行跑全套。
4. 保持现有 FastAPI Core + Browser Worker + SQLAlchemy/Alembic + `unittest`；不为测试便利无理由引入 pytest、新测试框架或全新项目骨架。
5. 旧功能、数据及历史账本不能因为新 UI 或玩法重构而牺牲；不改已发布迁移或旧规则快照。
6. 所有声称“完成/已验证”的功能须有**具体测试或真实平台证据**；缺协议、依赖或测试库时标记阻塞，不猜测，不虚构。

### 1.1 一次性基线，后续增量复用

首次进入仓库或大版本切换时，最多一次检查：

```bash
 git status --short
 git rev-parse --short HEAD
 rg --files dzmm_bot tests docs | sort
 rg -n '^class .*Tests|^    (async )?def test_' test_*.py
```

记录当前提交、已修改文件、测试分布、依赖和未解决的阻塞项到 `docs/ruihe-progress.md`；后续会话先读此文件与 `git diff --stat`，不再从头扫描。

本指南编写时看到的**旧 ZIP 环境基线**：`python -m unittest test_game -q` 通过 23 个用例；`python -m unittest test_bot -q` 通过 3 个用例；`test_core` 在本分析环境缺少 `socketio`（pip 包 `python-socketio`）时导入失败，**不能将其记为产品测试通过或代码本身失败**。这些结果不是将来 Codex 环境的测试报告，运行后必须重新记录。

### 1.2 真正需要按需阅读的文件

| 任务 | 首选阅读范围 | 对应现有测试 |
|---|---|---|
| 原生引用、消息发送、昵称 | `dzmm_bot/gateway.py`、`worker.py`、`core.py`、`store.py`、`persistence/transport.py` | `test_core.py`；新增 `test_reply_transport.py` 后补跑 |
| 中文指令、帮助 | `application/command_router.py`、`presentation/messages.py` | `test_game.py:RuleTests`、`test_game.py:GameTests` |
| 牧场、账本、行情 | `application/services.py`、`domain/economy.py`、`persistence/schema.py` | `test_game.py:GameTests`、`RuleTests`、`AdminTests` |
| 新数据库字段/迁移 | `persistence/migrate.py`、`migrations/versions/`、`schema.py` | `test_game.py:MigrationTests` + 新迁移测试 |
| 加工厂、宠物、挖宝 | 只读对应新增 service/rules/presentation/migration | 对应新增 `test_ruihe_*.py` + 账本/收发关键用例 |
| 部署、进程 | `compose.yaml`、`docs/server-guide.md`、`smoke_test.py` | 冒烟测试与部署预检 |

**查找顺序**：`rg -n '符号|指令|表名' 目标目录` → `sed -n '起,止p' 文件` → 必要时看邻近调用链。不要在没有明确需要时 `cat dzmm_bot/*`、递归打印全仓库或把 `ruihe.md` 原样回传给用户。

## 2. Codex 每轮的标准执行流程

```text
接收单阶段/单问题
  ↓
读取 git diff / progress / 相关计划小节
  ↓
定位涉及文件与具体测试（不全仓反复阅读）
  ↓
记录本轮验收条件（通常 3–6 条）
  ↓
新增最小失败测试（bug/新需求）
  ↓
完成垂直切片，避免不相关重构
  ↓
相关测试一次 + 必要不变量测试
  ↓
修复失败项，只重跑失败/相关测试
  ↓
阶段/PR 结束：全套一次 + 条件式集成测试
  ↓
更新短状态文档，报告实测结论
```

**缺少环境依赖**：先对照 `requirements.txt` / `requirements.lock.txt`；允许在独立虚拟环境安装项目原有依赖；禁止为解决缺包而擅自改业务代码或删测试。依赖不可装时标 `BLOCKED` 并继续完成不依赖它的静态检查和测试。

**修 bug 特别规则**：先运行一个失败用例证明缺陷存在，修完重跑该用例、同模块相关用例；阶段收尾再跑全套。不要用“改变预期输出/跳过测试”掩盖业务错误。

## 3. 分层测试：只在必要时升级测试强度

| 级别 | 触发条件 | 内容 | 什么时候跑 |
|---|---|---|---|
| L0 静态 | 所有 Python 改动 | 语法编译、diff 检查 | 每个小切片完成后 |
| L1 定点 | 某函数、模块、文案变动 | 新增/受影响的单个 TestCase/方法、黄金输出 | 修改后第一轮 |
| L2 相关回归 | 一条业务链完成 | 所属测试模块 + 关键跨层不变量 | 小切片验收时 |
| L3 全套 | 每阶段收尾、准备提交 PR/合并 | 仓库所有 `test_*.py` | **集中跑一次**；失败后只重跑受影响集合，最终再全套确认 |
| L4 本地集成 | Core/Worker/出站/启动链变更，或阶段发布前 | `smoke_test.py`（独立临时库、simulate 模式） | 有对应风险时 / 发布前 |
| L5 数据库/真实平台 | 迁移、金额/并发、原生引用、上线 | SQLite 旧库迁移 + PostgreSQL 测试库 + 授权测试群人工验收 | 只在相关阶段、灰度前 |
| L6 经济模拟 | 产能、价格、税、物品、彩票池等经济规则变化 | 28 天确定性模拟与对账 | 经济阶段结束/发布前；不按每次样式修改重复跑 |

### 3.1 可复制命令（在仓库根目录执行）

```bash
# L0：快速静态检查（git 仓库内）
python -m compileall -q dzmm_bot
 git diff --check

# L1：精确到测试方法；按实际测试名替换
python -m unittest test_game.RuleTests.test_saved_message_snapshots -q
python -m unittest test_core.CoreTests.test_auth_isolation_and_atomic_dedupe -q

# L2：只测直接关联模块 / 类
python -m unittest test_game.RuleTests test_game.GameTests -q
python -m unittest test_core -q
python -m unittest test_bot -q

# L3：阶段结束后的集中全套
python -m unittest discover -s . -p 'test_*.py' -q

# L4：启动集成，脚本自建临时 SQLite 和 simulate Core/Worker
python smoke_test.py

# L6：经济规则更新后；先以临时输出避免反复修改仓库基准报告
python -m dzmm_bot.simulate_economy --output /tmp/dybot-economy-check.json
```

说明：Windows PowerShell 将 `/tmp/dybot-economy-check.json` 换成可写的临时文件路径；新阶段新增测试文件后，按真实模块名运行。`python simulate.py` 是管理 CLI 的模拟指令入口，**不是** 28 天经济测试；不要把二者混淆。

**输出降噪**：常规测试用 `-q`，不要默认 `-v`；成功只报告测试数/耗时/结论，失败只报告失败用例名、首个根因与相关末尾日志。可以把长日志写在**仓库外临时文件**；失败再定点查行号，不把几百行 traceback 反复复制进 Codex 对话。不能丢弃失败的退出码或只凭 `tail` 误判成功。

## 4. 修改类型 → 最小测试矩阵

> 表中为**本轮先跑的测试**。阶段完成仍须 L3；“新增测试”表示计划期望的新文件，旧 ZIP 未必存在，禁止照着不存在的文件运行后报告失败。

| 变更范围 | 首跑 | 不可省的增量断言 | 额外门槛 |
|---|---|---|---|
| P0：入站/回复/出站 | `test_core` 相关单测；新增 Reply 契约测试 | 两玩家消息 ID 不串、成功和错误都引用、超时不双发、`uncertain`、重启后元数据存在 | 真实群 Reply UI 验收；平台协议未核验=未完成真实引用 |
| P1：指令别名/消息排版 | `RuleTests`、指令定点集成、瑞禾快照 | 旧命令有效；输出动态值/缩进/进度/金额/错误反馈；未开放菜单不伪装可用 | 长消息真实客户端可读性 |
| P2：牧场喂食/亲密/天气 | `GameTests` 对应方法 + 新纯规则单测 | 12h/14h/断喂10h、收取幂等、旧动物兼容、容量及账本守恒 | 历史库迁移演练 |
| P3：金额/行情/买卖 | 规则/经济/账本测试 + 迁移测试 | 小数无浮点误差、5%买卖费、30min 限购、跨群共享、旧币单位不变义 | PostgreSQL 并发与旧库迁移、L6 |
| P4/P5：加工与 Buff | 新工厂测试 + 旧库存/账本/发送关键用例 | 原料扣减/失败回滚、取货不双得、升级工时、取消/加急竞态、面板非硬编码 | 迁移/多用户压力与 L6（涉及经济时） |
| P6：宠物 | 新宠物测试 + 库存、调度、玩家隔离测试 | 48h/3天/忠诚衰减、每日次数、种子不可刷、蛋/繁育不双领 | 定时/稀有概率模拟 |
| P7：挖宝、求购 | 新状态机与交易测试 + 账本测试 | 30s/60s、幂等、并发冻结保证金、撤单/逾期解冻 | 调度重启模拟 + L6 |
| P8：系统活动/金融 | 分玩法测试 + 管理/账户/调度/账本测试 | 单次结算、全服唯一、消费销毁/税费滚池、定时跨日 | 测试 PostgreSQL + L6 |
| 文档、纯注释 | `git diff --check`；有代码块时抽样校验 | 路径/命令/规则与代码一致 | 无须无理由跑 DB/浏览器/28天模拟 |

### 4.1 所有资产或消息修改都要覆盖的横向不变量

- **原指令引用**：主动命令关联 `room + message_id + sender`；群主动播报无引用；同群交错指令不误回。
- **幂等**：同一命令、支付、订单、开奖重试不会重复变更；不同群相同 message ID 应按真实去重键处理。
- **事务**：余额/库存/业务状态/账本/outbox 同成同败；失败不吞账或制造重复回复。
- **隔离与权限**：冻结/未加入、跨玩家 ID/跨群、错误输入、权限不足不会改资产。
- **时间与随机性**：固定 UTC `now`、显式本地日界线与确定性 seed；不靠真实 `sleep` 猜结果。
- **兼容**：旧指令、旧表、旧规则版本、未读旧 outbox 行和已有账号正常工作。

仅改某条文案时不要重复全套资产压力测试；修改共用 Store/货币/时间函数时必须向外扩展相关回归范围。

## 5. 消息输出的高效黄金测试

需求来源：`docs/reference/ruihe.md` 最后的**牧场面板、投产回执、加工厂面板**，再加上“所有玩家主动命令回复该玩家原消息”。

1. 为三类样例准备**固定时钟、固定玩家状态、固定价格快照**的 fixture，并以现有 `tests/fixtures/game-messages.json` / `RuleTests.test_saved_message_snapshots` 为写法参考；新增瑞禾快照文件时与旧快照分开。
2. 直接比较完整 UTF-8 字符串，覆盖 `——`、`｜`、全角空格 `　`、`▓░`、Emoji、换行、末尾中文指令；**不要无差别去空格或删掉动态字段**以让用例通过。
3. 易变化的余额、时间、昵称通过**输入 fixture 固定**，不要更新预期文本来掩盖业务公式错误。
4. 再补小量边界样例：空牧场、停产、0库存、满级、已完成线、长昵称、格式错误、分页消息。
5. **原生引用不应只测字符串**：单独断言出站任务持久化引用 ID，适配器请求载荷符合实测协议，真实测试群 UI 确实显示“回复原消息”。

**修改快照审批规则**：只有已确认的产品文本要求变化才更新 golden；报告列出关键变化（标题/字段/单位/指令），禁止整文件机械重录实际输出。

## 6. 数据库、资金和外部协议的专属门槛

### 6.1 Alembic / 历史库

- 新版只追加版本（从当前 `0002_ranch` 往后），不修改已发布 `0001_foundation`、`0002_ranch`、旧配置快照和不可变账本。
- 用**独立临时 SQLite**测试空库 `upgrade head`、有旧玩家/旧 outbox 的 M1 历史库升级、重复启动/重复迁移、迁移后余额/昵称/账本行数一致。
- 币单位由整数币变为最小单位或小数时，另测旧币余额、所有历史交易、总奖池、返还和排行榜；不能只测新建账户。
- 涉及并发锁、JSON/索引、PG 专属语法或大额资金：在**测试用 PostgreSQL**执行同类迁移、并发、回滚和对账；本地 SQLite 通过不等于 PostgreSQL 已验证。
- 不对正式库运行测试或 `alembic downgrade`；上线前备份、备份副本迁移演练、前后对账，说明应用回退与数据恢复的区别。

### 6.2 Reply / 平台发送

- **先拿到平台真实字段协议**，再写精确请求契约 fixture；未知的 `reply_to` / `quote` 等命名一律记为待验证。
- mock 包括明确拒绝、429、断网/超时、ack 缺 ID、源消息失效、分页连续回复；超时之后任务为 `uncertain`，不自动换通道再发。
- 真实平台验收只用**授权测试群**，两名玩家交错发送 `/加入`、`/牧场` 和错误指令；同时检查 Bot API/Socket 可用路径，不向测试日志写 cookie/token 或真实私聊内容。

### 6.3 `smoke_test.py` / 28天模拟的使用边界

- 现有 `smoke_test.py` 用临时 SQLite、`simulate` 模式启动 Core/Worker，检查四条旧指令以及 **余额总计 47、奖池 3** 等 M1 数字。经济规则更新后这些断言可能需要**依据新已确认规则重算**；不得为了绿灯删除守恒检查，也不能拿它当“原生 Reply 实际平台已通过”的证据。
- 现有 28天模拟采用 M1 玩法、固定时间/seed、独立 DB、逐日核对账本；瑞禾更改经济规则后要**同步维护模拟行为与指标**，保留旧 M1 规则版本的独立回归。运行前先确认它测试的到底是旧规则还是新规则。
- `docs/economy-simulation-28d.json` 是已保存的参考报告；**临时测试输出不要覆盖它**，只有批准更新模拟策略时才提交新版基准报告及说明。

## 7. Token 节约约定（Codex 必须遵守）

| 要做 | 不要做 |
|---|---|
| 每轮读取 `git diff --stat`、进度文件和当前任务的计划小节 | 每一轮重新完整复述整个 P0–P9 计划 |
| 通过 `rg` 定位函数、`sed` 只看所需范围 | 把每个源码/测试文件全部贴回聊天 |
| 以“目标→关键变更→验收→测试结果→阻塞”输出 | 输出长篇逐步思考、冗余文件内容和重复命令流水账 |
| 小切片用 L1/L2；阶段末 L3 一次；发布前条件式 L4–L6 | 每改一行都跑所有测试、重建镜像、做 28天模拟 |
| 一次生成需要的相关测试用例；集中定位根因 | 失败时盲目反复重跑整个测试集 |
| 复用现有 service、ledger、配置快照和 fixture | 平行造一套框架、重复定义测试工具和游戏规则 |
| 缺失规则集中追加一条开放问题，标出阻塞阶段 | 因零散未定问题不停回问、猜默认值或假装功能完成 |
| 使用短状态文档跨会话续做 | 下次会话只凭聊天记录重建项目上下文 |

**不要用压缩报告取代真实测试。** Token 的节约应来自减少重复工具输出与重复工作，而非“测试没跑也写 PASS”。

## 8. 每阶段固定的短报告及跨会话接力

### 8.1 交付回报（建议 8–12 行，失败时可扩展）

```text
阶段/切片：P0 / Reply 元数据贯穿
结果：DONE | PARTIAL | BLOCKED
变更：文件A、文件B、迁移0003…（列路径，不粘贴整段diff）
行为：成功和错误指令保留 room/message_id/sender；旧 outbox 可读
测试：L0 PASS；L1 n/n PASS；L2 n/n PASS；L3 未到阶段收尾
外部：真实群 Reply 未验证（缺平台协议）；PG 不涉及/未运行
风险：网络超时维持 uncertain；无重复投送
阻塞：平台原生 Reply 真实载荷待取得
下一步：仅处理……
```

状态用词：`PASS`=确实运行通过；`FAIL`=确实运行失败；`BLOCKED`=被缺依赖/协议/权限阻挡；`NOT RUN`=此轮按矩阵无需执行；不要使用模糊“应该没问题”。

### 8.2 `docs/ruihe-progress.md` 最小状态格式

```markdown
# 瑞禾开发进度
基准提交：<sha>｜当前分支：<branch>｜当前阶段：P0｜最近验收：<日期>
已完成：<至多 5 项，指向代码/测试>
正在做：<只写 1 个垂直切片>
验证结果：<命令 + PASS/FAIL/BLOCKED；如有，附简短原因>
开放阻塞：<只列阻断下一步的 1–3 项，其他集中到 open-questions>
下一轮入口：<准确文件、测试、待做动作>
```

更新进度文件**不要每轮复制整份长计划**；已解决的历史过程放 Git 提交/PR 中。每阶段一个可回滚提交/PR（迁移一旦应用于生产不保证物理可逆）。如用户没有明确允许部署，只交付代码、测试和上线建议，不访问生产数据/发送生产群消息。

## 9. 三段可直接给 Codex 的节省 Token 提示词

### A. 开始一个阶段
