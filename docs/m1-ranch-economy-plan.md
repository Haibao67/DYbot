# M1 执行方案：牧场经济闭环

## 1. 前置条件与目标

M1 建立在 M0 已上线且账本对账稳定的前提上。它交付“购买动物 → 喂养 → 产出 → 收获 → 出售 → 升级”的完整牧场循环，并将每笔消费和出售的 5% 税收注入全局彩票奖池。

M1 不实现果园、马厩、赛事、彩票购票/开奖或竞猜。`world_state.lottery_pool_balance` 只累积税额，不向玩家派奖。

## 2. 已定稿规则

| 项目 | 规则 |
|---|---|
| 牧场等级 | 初始 Lv.1，最高 Lv.9，容量 `floor(3 + 2L)` |
| 升级 | L 升 L+1 费用 `round(200 × 1.5^(L-1))`；付款后立刻生效，不暂停生产 |
| 动物 | 鸡：空间 1、50 币、1 饲料、2–4h、鸡蛋售价 5；羊：空间 2、120 币、2 饲料、10–14h、羊毛售价 20；牛：空间 3、300 币、3 饲料、6–10h、牛奶售价 15 |
| 饲料 | 2 币/单位 |
| 生产期 | 新购动物自带 48h；每次喂食消耗饲料并重置为 48h |
| 产出间隔 | `I_base / (1 + 0.1 × (牧场等级 - 1))`；每个生产周期在开始时确定基础随机间隔 |
| 市场价格 | `基础价 × (1 + 0.15 × sin(2πt/24 + φ))`，展示与结算均按卖出时的服务器时间；结果向下取整到整数币，最低 1 币 |
| 流通税 | 购买动物、饲料、牧场升级、出售产品均收 5%；购买额外扣税，出售从所得扣税；税额 `ceil(成交额 × 0.05)` |

产品相位为鸡蛋 `0`、羊毛 `π/3`、牛奶 `2π/3`。`t` 为 UTC 时间转换到香港时间后的当天小时数（包含分钟的小数）。

## 3. 数据模型与配置

### 3.1 配置版本

把动物、价格、相位、容量公式、税率、生产期和升级公式放入 M1 的 `game_config_versions`，应用服务只读已发布版本。每次购买、喂食、产出和出售记录 `config_version`，以后调整平衡不篡改历史。

### 3.2 新表

| 表 | 关键字段 |
|---|---|
| `ranches` | `player_id PK`、`level`、`used_capacity`、`config_version`、`version`、`created_at` |
| `ranch_animals` | `id PK`、`player_id`、`animal_type`、`space`、`feed_cost`、`base_interval_hours`、`production_until`、`next_production_at`、`last_settled_at`、`status`、`rule_version` |
| `ranch_products` | `id PK`、`player_id`、`product_type`、`quantity`、`source_animal_id`、`produced_at`、`collected_at`；`(source_animal_id, produced_at)` 唯一 |
| `market_transactions` | `id PK`、`player_id`、`kind`、`gross_amount`、`tax_amount`、`net_amount`、`item_code`、`quantity`、`source_room_id`、`config_version`、`created_at` |

库存中的 `feed`、`egg`、`wool`、`milk` 是当前数量投影。`ranch_products` 保存来源与生成事实，收获后通过 `inventory_ledger` 写入库存；出售则从库存扣除并写 `market_transactions` 与货币账本。

## 4. 领域规则与原子操作

### 4.1 统一计税

```text
tax(gross) = ceil(gross × 0.05)
购买应付 = gross + tax(gross)
出售实收 = gross - tax(gross)
```

购买和升级在同一事务中扣“应付”、向奖池系统账户记税额、写交易单并变更资产。出售在同一事务中锁定库存、扣物品、向玩家记“实收”、向奖池记税额、写交易单。出售时 `gross` 不能低于税额；依照当前最低售价可保证实收至少为 1。

### 4.2 购买饲料

`/牧场 购买 饲料 <数量>`。数量必须是正整数，`gross = 2 × 数量`。余额不足或账户冻结时拒绝，不产生部分购买。成功后增加饲料库存。

### 4.3 购买动物

`/牧场 购买 <鸡|羊|牛> [数量]`。一次购买逐只创建动物，保证每只动物拥有独立生产时钟和随机种子。先计算总空间与总价格，检查 `used_capacity + space <= capacity(level)`，再统一扣款并插入动物。

新动物从购买成功时开始生产期：`production_until = now + 48h`；根据该动物购买事件的确定性随机数决定首次 `next_production_at`。不允许批量购买后合并为一只动物。

### 4.4 喂食

`/牧场 喂食 <动物编号>`。先按当前时间结算该动物在旧生产期内已完成、尚未收获的产出，再检查饲料库存，扣对应数量并把 `production_until` 重置为 `now + 48h`。下一次产出从 `now` 起重新抽取，不保留旧的剩余间隔。

已在生产期内提前喂食同样重置 48h；这符合原规则。不能使用负数、跨玩家 ID 或已停产动物。

### 4.5 惰性产出与收获

不为每个动物建立定时任务。任何 `/牧场 查看`、`收获`、`喂`、`卖` 操作都先执行 `settle_due_production(player, now)`：

1. 查询玩家处于生产期且 `next_production_at <= min(now, production_until)` 的动物并加锁。
2. 从上个结算点起，按已冻结的间隔/种子生成所有到期产品；每条产品记录用动物 ID 与产出序号唯一化。
3. 推进 `next_production_at`，直到其大于有效结束时间。
4. `收获` 将尚未收取的产品批量转入库存并写库存账本；不能直接把产品变成冬宴币。

首版单次结算最多生成 1000 条产品记录；超过时分批继续处理并向玩家提示，防止长期离线账户占用事务过久。

### 4.6 出售

`/牧场 出售 <鸡蛋|羊毛|牛奶|全部> [数量]`。先结算并收获可领取产品，再按卖出时市场价格计算每种产品的毛收入、税和实收。`出售 全部` 逐品类独立计算价格与税，在同一事务内完成。

回复应清楚列出：品类、数量、单价、毛收入、税额、实收、当前余额、当前奖池累计税额；不要把税隐藏在一个总价里。

### 4.7 牧场升级

`/牧场 升级`。等级为 9 时拒绝；否则按当前等级计算毛价与税，成功支付后立刻将等级加 1。`used_capacity` 不变，容量由新等级公式实时计算；升级不影响任意动物的生产期、产出间隔快照或下一次产出。

## 5. 命令与回复

### 5.1 回复规范落地

沿用总体架构的回复原则，M1 模板以 `🌾` 标记牧场，用 `🐔`、`🐑`、`🐄` 标记动物与产品，用 `📦` 标记收获，用 `💰` 标记出售，用 `🪙` 标记余额，用 `🎟️` 标记税额和奖池。每个 Emoji 必须表达实际状态，不使用连续装饰性符号。

回复固定先给结果，再以字段行展示关键数字，最后仅给一个适合当前状态的后续动作：

```text
✅ 出售完成 💰
鸡蛋 ×12｜单价：⨀ 5
毛收入：⨀ 60｜🎟️ 税：⨀ 3
实际到账：⨀ 57｜🪙 余额：⨀ 241

输入 /牧场 查看 查看生产状态
```

购买、喂食、收获、出售和升级都必须展示最终已提交的金额、数量及余额；容量不足、饲料不足、产品不足、余额不足和满级以 `⚠️` 开头，并说明缺少的空间/数量/金额或恢复条件。`/牧场 查看` 优先呈现等级、容量、可收获产物和即将停产项，长动物列表最多 5 项。

```text
/牧场 查看
/牧场 购买 饲料 <数量>
/牧场 购买 <鸡|羊|牛> [数量]
/牧场 喂食 <动物编号>
/牧场 收获
/牧场 出售 <鸡蛋|羊毛|牛奶|全部> [数量]
/牧场 升级
```

`查看` 以 `🌾 我的牧场` 为标题，展示等级、已用/总容量、动物摘要、饲料、产品库存、当前市场单价、可收获数量、生产期即将结束的动物。动物 ID 用短展示 ID，解析时仍映射到完整 UUID 且必须归属当前玩家。

所有玩家可见命令、帮助说明和下一步引导均为中文；内部英文枚举、函数名与数据库字段绝不出现在回复中。所有变更回复都带交易/操作编号；重复命令消息返回首次成功结果或“已处理”，不再购买、扣饲料或出售。

## 6. 开发顺序

1. 发布 M1 配置版本，新增表与迁移；补 `world_state` 的奖池系统账户约束。
2. 实现 `TaxPolicy`、容量/价格/生产间隔纯函数及固定种子随机工具，先完成单元测试。
3. 实现 `RanchService.create_ranch_if_missing`、买饲料、买动物和升级。
4. 实现动物生产结算、收获、喂食，覆盖重启与长时间离线。
5. 实现出售、奖池入账、交易回执和牧场展示。
6. 将 `/牧场` 接入 `CommandRouter`，扩展 `/帮助`，增加管理查询接口与运营指标。
7. 用模拟玩家运行 28 个游戏日，再在测试群灰度开放。

## 7. 测试矩阵

- 容量：每级边界、批量购买、升级前后可用空间、不同动物混合。
- 金额：每种购买和出售的 5% 向上取整、余额不足、出售后最低实收、奖池账本总和。
- 生产：48h 边界、随机间隔边界、提前喂食、停产、重启、同一到期批次重复结算。
- 库存：收获与出售并发、卖全部、零库存、跨玩家动物 ID、数量溢出与非法输入。
- 市场：三个相位、香港跨日、价格取整、服务器时间而非客户端时间。
- 幂等：重复入站消息、业务唯一冲突、Worker 重试、事务中断后重跑。
- 回归：M0 的 `/加入`、`/我的`、`/救济`、发件箱顺序与房间授权继续有效。
- 模板快照：购买、喂食、收获、出售、升级及全部拒绝分支均符合标题、Emoji、金额标签、税额和单一下一步指引规范。

## 8. 灰度与验收

### 灰度节奏

1. 开发库：自动测试和 28 日模拟，无人工资产。
2. 测试群：仅白名单玩家，先开放购买、查看、喂食、收获，不开放出售 24 小时。
3. 小范围开放：启用出售与税收，连续观测 72 小时。
4. 正式开放：指标稳定后向所有已启用群开放。

### 上线指标

- 账本余额与账户投影差额必须为 0。
- 奖池累计税额必须等于所有 `market_transactions.tax_amount` 之和。
- 每个动物的产品数与可复算生产时钟一致。
- 重复命令导致的重复经济交易数必须为 0。
- 监控每日币产出、税收占比、饲料消耗、动物类型分布和新玩家在 7 天内的余额变化。

达到上述指标且测试群无无法人工解释的账本差异，M1 才可验收并进入赛马 M2。
